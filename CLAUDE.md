## Commands

There is no build step, package manager, linter, or test suite — this is a static site (plain HTML/CSS/JS).

- **Run the app**: open [index.html](index.html) directly in a browser (works from `file://`), or serve the directory with any static server (e.g. `npx serve .`).
- **No install, build, lint, or test commands exist.** Do not add a `package.json` or tooling unless the user explicitly asks for it — the no-build-step constraint is intentional (see below).

## Architecture

Single-page app: [index.html](index.html) mounts an empty `#app` div, [style.css](style.css) holds all styling, and [app.js](app.js) (~1190 lines) contains all state, rendering, and logic. No frameworks, no modules, no bundler.

**Rendering model**: one global `state` object + a single `render()` function that rebuilds `#app`'s entire `innerHTML` from scratch on every change (`app.js:1030`). There is no virtual DOM and no partial patching, except:
- The countdown timer updates its own DOM node directly every second via `updateTimerDom()` (`app.js:610`) instead of going through full `render()`, for performance.
- `render()` manually preserves focus and text-selection range across the re-render (`app.js:1030-1061`), since rebuilding `innerHTML` would otherwise drop focus while typing.
- The currency-converter dropdown panel is `position:fixed` and its `top`/`left`/`width`/`max-height` are computed and written directly to its DOM node by `positionCurrencyDropdown()` (`app.js:355`), called at the end of every `render()` — CSS alone can't position it (it must escape the modal's own `overflow:auto` clipping on mobile, see below), so this is the one other deliberate exception to "render rebuilds everything declaratively." It also re-runs on `visualViewport`'s `resize`/`scroll` events (wired in `init()`), since opening it no longer assumes there's more room above the button (see below).

**Event handling**: fully delegated at the root `#app` element — one `click`, `input`, `change`, and `keydown` listener each, attached once in `init()` (`app.js:1175-1184`). Individual elements are never given their own listeners; instead:
- Clickable elements carry `data-action="..."` (and often `data-id`/`data-idx`/`data-tab`/etc.), dispatched through the `switch` in `onRootClick()` (`app.js:1108`).
- Form inputs are matched by DOM `id` against the `INPUT_BINDINGS` map (`app.js:1065`), which writes the typed value into `state`.
- Enter-to-submit fields are declared in `SUBMIT_ON_ENTER` (`app.js:1098`), mapping an input's `id` to an action name resolved via `SUBMIT_ACTIONS` (`app.js:1089`).

When adding a new interactive element, follow this pattern: add a `data-action` handler in `onRootClick`, or add the input's `id` to `INPUT_BINDINGS` (and `SUBMIT_ON_ENTER`/`SUBMIT_ACTIONS` if it should submit on Enter) — don't attach ad-hoc listeners.

**State shape** (`app.js:127`): one active/working trip is flattened into top-level `state` fields (`days`, `budgetTotal`, `expenses`, `todoBefore`, `todoDuring`, `tripName`, `tripStart`, …) plus UI state (`activeTab`, `activeDayIdx`, in-progress drafts and their error flags, modal state). `state.trips[]` holds saved snapshots of *all* trips; the active trip is copied out into the flat fields via `applyTripToState()` and copied back in via `collectTrip()` when switching trips (`app.js:312-331`).

**Persistence — autosave, no manual save button**: single `localStorage` key `tp-trips-v2` (`TRIPS_KEY`, `app.js:11`), storing `{ trips, currentTripId }`, written by `persist()` (`app.js:175`). There is no "Save" button — `render()` calls `scheduleAutoSave()` on every re-render (`app.js:1061`), which debounces 600ms (`app.js:466-474`) before merging the flat state fields into `state.trips` via `collectTrip()` and calling `persist()`. A `beforeunload` listener (`app.js:1184`) calls `flushAutoSave()` synchronously as a safety net in case the tab closes mid-debounce. `switchTrip()`/`createTrip()`/`deleteTrip()` still persist immediately and unconditionally (they don't rely on the debounce) since they swap or remove which trip is active. On first load with no saved store, `loadStore()` seeds a default "טיול לונדון" (London) trip from the `SEED_*` constants (`app.js:39-109`) and persists it immediately. When adding new mutating actions, no extra persistence call is needed — just end the action with `render()` as usual and autosave picks it up.
Note: the currency converter's fields (`currencyFrom`, `currencyAmount`, etc., `app.js` state block) are UI-only and deliberately **not** part of `collectTrip()`/`applyTripToState()` — they're global preferences, not per-trip data, so they persist across trip switches but are never written to `localStorage`. `currencyFrom` specifically gets overwritten each time the modal opens by `guessTripCurrency()` (see Currency converter below) — that's a one-shot default, not persisted per trip either.

**RTL/Hebrew**: the entire UI is Hebrew with `dir="rtl"` (set in [index.html](index.html)). All user-facing strings are Hebrew literals inline in `app.js` — there is no i18n layer. Keep new UI text in Hebrew and RTL-consistent.

**Font**: Rubik, loaded from Google Fonts via a `<link>` in [index.html](index.html) and set as the primary face in `--font-stack` ([style.css](style.css)'s `:root`), with system-font fallbacks for offline/`file://` use.

**Header layout**: [app.js](app.js)'s `renderHeader()` (`app.js:630`) renders two explicit flex rows (`tp-headerrow1`, `tp-headerrow2`) rather than one wrapping row:
- Row 1 holds an app-level eyebrow title ("תכנון הטיול הבא שלי", styled the same size/weight as the trip name) above the title block — trip name, year badge, and a **single** pencil (`edit-trip-info`) that toggles both the name and the date into inline-editable inputs together, saved/cancelled as one unit via `saveTripInfo()`/`cancelEditTripInfo()` (`app.js:525-547`). Don't split name-editing and date-editing back into two separate pencils — they were merged deliberately so there's exactly one edit affordance for "trip info."
- Row 2 holds `tp-tripbar-col`, a column stacking the trip-selector row (`tp-tripbar`: NEW button + `<select>` + a delete-trip icon button acting on the currently-selected trip via `deleteTrip()` (`app.js:489-500`), guarded by a `confirm()` and blocked when it's the only remaining trip — no Save button, see Persistence above) directly above the countdown timer (`.tp-timer`, driven by `computeCountdown()`/`renderTimerBody()`, `app.js:577-609`); then the tab nav in order מסלול יומי → תקציב והוצאות → צ'ק-ליסט (first in DOM renders rightmost under RTL).

Keep new header controls in one of these two rows rather than reintroducing a single flat row.

**Icons**: all icons are inline SVG strings in the `ICO` and `ICON_PATHS` objects (`app.js:19-38`) — no icon library, no image assets. The one exception is currency flags (see below), which use real SVG images from an external CDN instead, since Windows browsers have no color flag-emoji glyphs to fall back on.

**Currency converter** (budget tab, `app.js:291-465`, in the BUDGET section): a modal (`renderCurrencyModal()`) opened via `open-currency-converter`, converting between ~50 currencies live against `open.er-api.com` (`CURRENCY_API`, free, no key, updates once daily at the source — the app fetches fresh on every conversion, it doesn't cache rates). Currency names (`CURRENCY_NAMES`) and their flag-icons country codes (`CURRENCY_COUNTRY`) are curated static maps in `app.js`, not fetched — covers the existing majors plus South America, the Gulf states, and Eastern Europe; extend both maps together when adding a currency.
- **Destination auto-guess**: `openCurrencyConverter()` runs `guessTripCurrency(state.tripName)` and, if it matches, sets `currencyFrom` to it before the modal renders — so e.g. a trip named "טיול לונדון" defaults the "מ-" (right-hand) field to GBP instead of whatever was last selected. `guessTripCurrency()` scans `TRIP_DESTINATION_CURRENCY` (`app.js:333`), a curated list of `[hebrew keywords[], currency code]` pairs (cities/countries), checking `tripName.includes(keyword)` in order — first match wins, so more specific keywords are listed before broader ones. It only ever resolves to a currency already in `CURRENCY_NAMES`/`CURRENCY_COUNTRY`; add destinations there, not new currencies. If no keyword matches, `currencyFrom` is left untouched (the user's last manual choice).
- **Custom dropdown, not `<select>`**: the from/to pickers (`renderCurrencyCombobox()`) are hand-built button+panel combos (`toggleCurrencyDropdown()`/`selectCurrency()`/`closeCurrencyDropdown()`), not native `<select>` elements. This was deliberate — a native `<option>` can only ever render plain text, so a per-row flag icon is impossible in a real `<select>`'s popup (confirmed by testing: flags showed only in the closed box, never while scrolling the native list). The dropdown panel is `position:fixed` (see `positionCurrencyDropdown()` above) specifically so it can escape the modal's own scroll clipping and use the full screen height rather than a fixed `max-height`.
- **Mobile-keyboard positioning**: `positionCurrencyDropdown()` opens the panel toward whichever side (up or down) currently has more visible room, measured against `window.visualViewport` (not `window.innerHeight`) — the visual viewport shrinks and its `offsetTop` moves when the iOS keyboard is up or the page auto-scrolls a focused input into view, so a naive "always upward against full window height" calculation left the panel clipped or floating in the wrong place once the amount field's keyboard was open. `toggleCurrencyDropdown()` also blurs `document.activeElement` before re-rendering, since iOS Safari doesn't move focus to a tapped `<button>` — without the explicit blur, the amount input (autofocused on modal open) would stay focused and its keyboard would stay up across the toggle.
- **Flags**: `<span class="fi fi-xx">` from the [flag-icons](https://github.com/lipis/flag-icons) CDN stylesheet (linked in [index.html](index.html)) — real SVGs, not Unicode flag emoji, because Windows ships no color flag glyphs in any browser (a platform limitation, not a browser bug) and the earlier emoji-based attempt rendered as bare two-letter codes there.
- **Bidi gotcha**: any UI text mixing digits with Latin currency codes (`"10 GBP = 40.43 ILS"`, the combobox's own label, dropdown rows) needs an explicit `direction:ltr` — left to inherit the page's `dir="rtl"`, the browser's bidi algorithm reorders the amount to the wrong end of the string. Every currency-related text node in [style.css](style.css) sets `direction:ltr` for this reason; carry it forward if you add another one.
- Result-line formatting: `fmtCurrencyResult()` (`app.js`, near `fmtNum`) shows 4 decimals instead of `fmtNum`'s flat 2 when the converted amount is under 1 — otherwise low-value currencies (ARS, COP, PYG…) round display to a misleading "0.00".
- Unlike the Rubik font (which has a system-font fallback), this feature has no offline fallback: rates fail with `currencyError`'s message, and flags with no CDN just render as blank chips — both fail quietly, nothing crashes.

**Budget stat cards** (`renderBudget()`, `app.js:875`): the total/spent/remaining cards show plain numbers with no currency-symbol prefix — `DEFAULT_CURRENCY` (`£`) was removed from them since a trip's real currency now varies by destination (see the auto-guess above) and there's no single fixed symbol to label these with. `DEFAULT_CURRENCY` is still used as a placeholder hint in the add/edit item price inputs.
